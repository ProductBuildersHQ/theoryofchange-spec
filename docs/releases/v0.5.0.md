# Release Notes v0.5.0

Released: 2026-11-01

The problem tree joins the projections of an impact model. It puts the problem
a program exists to solve in the middle, its causes below as roots, and its
effects above as branches, and checks that every cause and effect is addressed
by an outcome or set aside with a reason. Causes, and the new effects, form a
network: each can lead to several others.

This release has one breaking change: a cause's `parent` is now `parents`, a
list. See [Upgrading](#upgrading).

## Highlights

- **Problem trees.** `report problem-tree` draws the core problem with causes
  below and effects above, arrows flowing upward from the deepest causes to the
  furthest effects, and lists what addresses each.
- **Effects.** The problem tree's branches: what the core problem leads to.
  Outcomes name the effects they relieve with `addressesEffects`.
- **A network, not only a tree.** A cause can contribute to several others and
  an effect can follow from several, so `parents` is a list.
- **JSON first.** The diagram is built as a JSON diagram document, from which D2
  and Mermaid are rendered, and `report problem-tree-json` prints it.

## New Features

### Problem tree reports

```bash
impact-model report problem-tree impact-model.yaml        # Markdown, with a Mermaid diagram
impact-model report problem-tree-d2 impact-model.yaml     # the same, with a D2 diagram
impact-model report problem-tree-json impact-model.yaml   # the diagram document itself
```

| Diagram | In the model |
|---------|--------------|
| Core problem, in the middle | `context.problemStatement` |
| Causes (roots), below | `causes`, each leading to its `parents` or to the core problem |
| Effects (branches), above | `effects`, each following from its `parents` or from the core problem |
| What addresses a cause | an outcome's `addressesCauses` |
| What relieves an effect | an outcome's `addressesEffects` |

The core problem is in the middle row. A cause is one row below its lowest
parent and an effect one row above its highest, so every arrow points up. A
cause or effect set aside is drawn faded, and a rejected one is left out. The
JSON report is the [d2vision](https://github.com/grokify/d2vision) diagram spec
both renderings come from, written without the Markdown stamp so it stays valid
JSON. The [problem tree guide](../guides/problem-tree.md) explains each part.

### Effects

```yaml
effects:
  - id: eff-diabetes
    statement: Diabetes and heart disease
  - id: eff-costs
    statement: Higher health costs
    parents: [eff-diabetes]
outcomes:
  - id: oc-eat-well
    title: People eat well
    level: impact
    addressesEffects: [eff-diabetes]
```

An effect has a statement, the effects it follows from, affected groups,
evidence, an optional out-of-scope reason, and provenance. Validation reports an
effect without a statement (VAL-EFF-001), one among its own parents
(VAL-EFF-002), a chain of parents that loops (VAL-EFF-003), and one set aside
without a reason (VAL-EFF-004). The `effect` element command adds and changes
effects, and `outcome set --relieves` names the effects an outcome relieves.

### Causes as a network

A cause's `parents` are the causes it contributes to, so structural causes feed
underlying ones, underlying feed immediate, and immediate causes lead to the
core problem. Validation now finds a loop through any branch of the network.
Causes also take provenance, so one can be rejected in review like other
elements.

### Lint

Three new rules, 72 in all:

- `IMP-EFF-001`: each effect is relieved by an outcome or set aside with a reason
- `IMP-EFF-002`: effects are relieved by long-term or impact outcomes, not only
  by earlier ones
- `IMP-CAU-003`: a cause contributes only to causes at its own level or nearer
  the problem, which catches a link written the wrong way round

The cause rules now skip rejected causes.

### Examples

The examples linked their causes the wrong way round, from the nearer cause to
the deeper one, and now point from deeper causes toward the problem. In the
membership network, working alone feeds both of the immediate causes. Both the
membership network and the course catalog gain the effects of their core
problems, each relieved by a long-term or impact outcome.

## Upgrading

### Documents: `parent` is now `parents`

A cause that names a parent must name it in a list. Validation refuses the old
field:

```
error VAL-SCH-001 /causes/2: additional properties 'parent' not allowed
```

```yaml
# was
causes:
  - id: cause-fast-food
    level: underlying
    parent: cause-busy

# is
causes:
  - id: cause-fast-food
    level: underlying
    parents:
      - cause-busy
```

In JSON, `"parent": "cause-busy"` becomes `"parents": ["cause-busy"]`. Nothing
else in a document changes; `specVersion` stays `"0.1"`.

While you are there, check which way the links point. A cause's parents are the
causes it contributes to, nearer the problem. If an immediate cause names an
underlying or structural one as its parent, the link is reversed, and
`IMP-CAU-003` now reports it.

### Command line

`cause add` and `cause set` take `--parents`, which accepts several IDs, in
place of `--parent`.

### Go code

`impact.Cause.Parent string` is now `Parents []string`. Other changes are
additions: `impact.Effect`, `Model.Effects`, `Outcome.AddressesEffects`,
`Cause.Provenance`, and the `problemtree` package.

## Compatibility

An API comparison against v0.4.0 reports one incompatible change, the removal of
`Cause.Parent`, and the additions above as compatible. The command line keeps
its exit codes, and a model with no causes or effects is unaffected.

## Known Limitations

- **Labels are not wrapped,** so a long problem statement makes a wide box. Keep
  the core problem to a short phrase and put the detail in the narrative.
- **Row order is file order,** so arrows between rows can cross; reorder causes
  or effects in the file to change it.
- **Mermaid places rows itself.** Only the D2 rendering keeps every row in place.
- The limitations of [v0.4.0](v0.4.0.md#known-limitations) still apply.
