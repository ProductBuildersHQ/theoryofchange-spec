    PLAN — Theory of Change Specification — Go-first model, JSON Schema, measurement, and leadership reporting¶

    Initiative: INIT-THEORYOFCHANGESPEC-001 Repository: github.com/ProductBuildersHQ/impact-model Version: 0.4 Status: Draft — pending tech-lead review (pbhq-lite gate: after PLAN)

    This PLAN is non-normative. It sequences the work in PRD.md and TRD.md and must not add requirements. Execution state lives in ROADMAP.md.

    1. Approach¶

    Thin slice first, then deepen. The first five phases build one complete path from end to end:

    minimal model → validate → edit → pathways, metric library, provenance → diagram, logic models, metric definitions, glossary, workshop deck, draft from public sources → assessment, review packet and sheet, review import, approval

    That path is the first adopter milestone: draft a theory from public information, share it as familiar documents, take the organization's responses back in, and approve the agreed baseline. Later phases add depth behind interfaces the slice has already proven.

    Why this order:

    1. Model, schema, load, validate, edit. Every consumer binds to the model. Every mutation goes through one validated patch engine from day one.
    2. Pathways, metric library, glossary, and provenance are the smallest additions a real organization needs. Provenance has to arrive with the first draft, because the first draft is typically built from public sources and every element must say whether it was stated or inferred.
    3. Workshop pack and source drafting. Diagram, logic models, metric definitions, glossary, CSV, a Marp workshop deck, and the draft-from-sources skill. Together they turn public sources into a presentable hypothesis theory.
    4. Review and agreement. The assessment report, the pandoc sharing profile with export stamps, the review packet and review sheet, review import as proposals, and approval. This closes the loop with people who never touch the tools. The loop is file-based, so it works with manual upload and download before any Google automation exists.
    5. Measurement-framework design. Metric selection and burden, stories, and UNDG change analysis.
    6. Quality. Lint profiles, the rubric, and judging.
    7. Measurement.
    8. Reporting, story, and presentations.
    9. Agents and revisions. The MCP server, skills, theory diff, and Google sharing automation. Google sharing waits on gogoogle and mcp-google (INIT-GOGOOGLE-001, INIT-MCPGOOGLE-001).
    10. Ecosystem integration and release.

    Major bets:

    • The ToC graph is primary.
    • ObservationSet is a separate document.
    • Shared metric definitions plus deterministic tools.
    • All edits go through validated patches.
    • Decks reuse the report view.
    • Judging is file-based.
    • Provenance lives on every element.
    • Review responses are a channel-neutral file (ReviewResponse) imported as proposals. Google Drive is one channel, reached through external tooling; this module stays free of cloud dependencies.

    Deliberately deferred:

    • contribution claims
    • substantiated observed outcomes
    • logframe matrices
    • XLSX
    • data connectors and record linkage
    • a hosted service
    • native PPTX generation in Go

    1.1 Adopter milestones¶

    The phases are ordered so a first adopter can use the tools at each stage of a ToC-based impact-measurement engagement. The adopter is a small-staff organization.

    Adopter milestone What happens Phases needed
    M0 — Hypothesis draft Draft the ToC from public sources; render the workshop pack and assessment 1–4
    M1 — Review, workshop, and agreement (thin slice) Share the review packet and sheet; workshop with live edits; import responses; approve v1.0 5
    M1.5 — Collection plan Score candidate metrics; set burden budget; collection plan 6
    M2 — First measurement cycle Load the first month's spreadsheet data; baseline status 8 (plus RMI 024)
    M3 — Mid-point learning Learning review; audience stories; decks; rubric review of the revised ToC 7, 9
    M4 — Handoff Staff run the routine through an AI assistant, including Google sharing 10

    5. Data and Migration¶

    Not applicable for v0.1. Pre-release documents are migrated with impact-model fmt and impact-model validate. The model only gets additive changes after Phase 6.

    6. Testing Strategy¶

    As in TRD §12, plus:

    • Provenance: rejected-element exclusion tests.
    • Review import: seeded rows covering every origin (sheet, table, comment, suggestion) and stale hashes.
    • Export stamps: checked for every format.
    • pandoc and mmdc: export tests skipped when the tools are absent.
    • Skills: smoke tests for impact-draft-from-sources (saved fixture pages) and toc-share-google (recorded gogoogle / mcp-google outputs).

    Coverage target ≥ 80 % on pkg/....

    7. Rollout and Rollback¶

    • Phase pre-releases. Each phase ends in v0.1.0-alpha.N. Adopter milestones pin the pre-release they used.
    • Final release. Phase 11 ends in v0.1.0.
    • Tagging. Tag only after CI is green.
    • Rollback. Pin the previous tag.
    • Adopter data stays out of this repository. Adopter documents, sources, evidence, observations, stories, review responses, decks, and verdicts live in the adopter's own repository or drive. This repo contains only fictional examples.
