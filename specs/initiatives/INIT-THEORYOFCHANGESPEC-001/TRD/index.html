    TRD — Impact Model Specification — Go-first model, JSON Schema, measurement, and leadership reporting¶

    Note on names. This specification was written when the product was called the Theory of Change specification. It is now the impact model, and the theory of change, the logic model, the outcome map, and the logframe are projections of it. Below, "theory" means the impact model document unless it names the method. See the decision.

    Initiative: INIT-THEORYOFCHANGESPEC-001 Repository: github.com/ProductBuildersHQ/impact-model Version: 0.1 Status: Draft

    This TRD is a technical contract: what the module MUST guarantee. MUST / MUST NOT / SHOULD / MAY are used in the RFC 2119 sense. Conditions that do not apply are answered Not applicable — <rationale>.

    1. Introduction¶

    1.1 Purpose¶

    Define the Go module github.com/ProductBuildersHQ/impact-model: a Go-struct-first Theory of Change (ToC) model, its generated JSON Schemas, and the library, CLI, and MCP tooling that validate, analyze, measure, judge, and report on ToC documents. This TRD lets implementation proceed phase by phase (PLAN.md) without inventing product decisions.

    1.2 Scope¶

    In scope: data model, schema pipeline, validation, causal-graph analysis, deterministic lint, measurement roll-up, report rendering, spec template and LLM-judge rubric, MCP server, PRISM adapters, and the USM/UFM integration contract.

    Out of scope: see PRD §2.2 (no USM/UFM implementation, no UI, no LLM calls, no persistence, no statistical inference).

    3. System Invariants¶

    • INV-1 Every element ID MUST be unique within a document across all element kinds (outcomes, links, interventions, assumptions, indicators, actors, evidence, factors, risks).
    • INV-2 No library function MAY mutate its input Model or ObservationSet; derived data is returned in new values.
    • INV-3 For identical inputs (documents, observation sets, asOf, options), every computed output (issues, status snapshot, report bytes) MUST be byte-identical. Map iteration MUST NOT influence output order; ordering is by document order, then ID.
    • INV-4 Unknown references MUST be reported, never silently dropped.
    • INV-5 A score shown to a reader MUST be accompanied by its inputs or a link to them (indicator observations, assumption assessments, evidence IDs).
    • INV-6 restricted evidence (and evidence with no sensitivity set) MUST NOT be rendered in any output intended for humans (Markdown, HTML, Mermaid labels).
    • INV-7 The library MUST NOT perform network I/O or execute external programs. Only cmd/ and pkg/mcp read or write files, and only paths given by the caller; only cmd/impact-model may invoke the optional external export tools (marp, mmdc, pandoc). The module has no Google or other cloud API dependency.
    • INV-10 Review imports never modify a document; they produce proposals that are applied only through pkg/edit (INV-9).
    • INV-8 Schema files MUST only change via cmd/generate-schema.
    • INV-9 Every change to a ToC document made by this module goes through pkg/edit; no other code path writes a modified document.

    4.3 Data Flow¶

    1. Load: impactio.LoadDocument(path) → bytes → (YAML→JSON) → schema validate → json.Unmarshal into impact.Model.
    2. Validate: validate.Model(doc) → issues. Lint and measure refuse to run on documents with error-severity validation issues (they return ErrInvalidDocument wrapping the issues).
    3. Graph: graph.Build(doc); reused by lint, measure, report.
    4. Measure: measure.Evaluate(doc, g, obsSets, opts) → impact.Status.
    5. Report: report.Build(doc, g, status, opts) → report.View → template → bytes.

    5. State and Lifecycle¶

    Applicability: Applicable.

    Entity States Trigger Invalid Transitions
    Document (metadata.status) draft → in_review → approved → active → archived (prism-core status constants) Author edits field None enforced by library (git is the audit trail); lint warns when active documents have open error findings
    Intervention planned, in_progress, completed, paused, cancelled Author edits None enforced
    Assumption untested, holding, at_risk, invalidated, validated Latest AssumptionAssessment in observation sets overrides the document's static status None enforced; history kept in observation sets
    Indicator status Computed: achieved, on_track, at_risk, off_track, not_started, no_data, stale, baseline_only measure.Evaluate Not stored by authors
    Indicator selection candidate → selected → retired (and candidate → retired) Author edits retired → selected requires a Revision entry (lint info)
    • Idempotency: All operations are pure functions of their inputs; re-running is safe.
    • Concurrency: Not applicable — no shared mutable state; files are owned by git.
    • Retention / deletion: Not applicable — documents live in git; the revision log records intent.
    • Terminal and recovery states: archived documents are still loadable and reportable.

    6. Interface Contracts¶

    6.1 CLI (cmd/impact-model)¶

    Flag conventions. -o / --out is the file a command writes, as in pandoc, marp, and mmdc; standard output is the default. -O / --observations names observation set files and may repeat. --as-of is the date an artifact describes. Exit codes are as in the table.

    Command Description Exit codes

    impact-model lint <toc> [--format table\|json] [--disable RULE] [--fail-on error\|warning] Deterministic quality rules; JSON is a SummaryReport 0 GO; 1 NO-GO; 2 error
    impact-model graph <toc> [--format mermaid\|json\|dot] [--from ID] [--paths] Graph export and queries 0; 2

    impact-model mcp Start MCP server on stdio 0 on clean shutdown
    impact-model patch <toc> <patch.json\|-> [--dry-run] [--allow-errors] Apply RFC 6902 patch atomically (§6.12) 0 applied; 1 rejected; 2 error
    impact-model <kind> add\|set\|rm … (kind ∈ outcome, group, link, intervention, assumption, indicator, metric, pathway, actor, evidence, cause, term) Element commands compiled to patches; rm --cascade; all accept --dry-run 0; 1 rejected; 2

    impact-model export review-sheet <toc> [--out file.csv] Review rows as CSV 0; 2
    impact-model export docx\|pptx <kind> <toc> [-O obs...] [--reference-doc file] Any report (docx) or deck (pptx) through the pandoc profile 0; 2; 3

    Global flags: --as-of (RFC 3339 date; default: today in UTC), --format, --quiet. All machine output goes to stdout; diagnostics to stderr.

    6.5 Measurement algorithms¶

    Indicator progress (quantitative). With baseline b, current c, final target t, direction d:

    • increase: p = (c − b) / (t − b); decrease: p = (b − c) / (b − t).
    • maintain: p = 1 if |c − t| ≤ tolerance else 0.
    • If t = b, p = 1 when the target condition holds, else 0.
    • p is clamped to [0, 1.5] for display; achieved when p ≥ 1.

    Expected progress at asOf. Targets form a time series (baseline.date, 0) → (target_i.date, p_i). Expected e is linear interpolation at asOf (0 before the baseline date, 1 after the final target). Indicator status:

    Condition Status
    no targets defined (baseline only) baseline_only (latest value reported, no progress computed)
    no observation and asOf < first target date not_started
    no observation and asOf ≥ first target date no_data
    last observation older than 2 × frequency stale
    p ≥ 1 achieved
    p ≥ e − tol (default tol = 0.10) on_track
    p ≥ e − 2·tol at_risk
    otherwise off_track

    Qualitative indicators use the ordinal position of the observed level in the indicator's ordered levels as c, with b and t as level positions.

    Health mapping (prism-core): achieved, on_track → green; at_risk, stale → yellow; off_track → red; not_started, no_data, baseline_only → no health (rendered grey). baseline_only ranks with not_started in roll-ups.

    Metric roll-ups. For an indicator with rollupFrom, the value at a date is computed from the latest source observations at or before that date using the metric's aggregation (weighted_mean weights by the latest value of weightMetricId's indicator in the same pathway). If any source lacks a value the roll-up is no_data and lists the missing sources. Direct observations of a roll-up indicator take precedence and the computed value is reported alongside for comparison.

    Theme counts. A theme_count indicator's value for a period is the number of stories in that period's observation sets tagged with any of its themeIds (optionally filtered by pathwayIds); stories are counted once.

    Collection burden (pkg/burden). Per selected indicator, staff minutes are normalized to minutes per week from collection.minutesPerPeriod and collection.period; respondent questions per year = questionsPerRespondent × (collections per year) × sampleRate. Totals are reported overall, per pathway, and per mode; budget comparisons feed TOC-BUD-*.

    Outcome status = roll-up of its indicators by Rollup option: worst (default) or mean of progress. Outcomes without indicators get unmeasured.

    Pathway status. Processed in topological order from the leaves upward. A node's precondition signal is computed over incoming non-feedback links: grouped sources are first reduced through their PreconditionGroup (nested groups innermost first), then the group results and ungrouped sources are combined with the outcome's logic: all → worst; any → best; at_least k → k-th best. Status ordering for worst/best is off_track < at_risk < stale < no_data < not_started < on_track < achieved. Pathway status = worse of (own outcome status, precondition signal), where unmeasured defers to the precondition signal.

    Assumption propagation. Effective assumption status = latest assessment in observation sets, else the document's static status. A link whose assumptions include invalidated is broken; at_risk makes it at_risk. Every outcome downstream of a broken link gets the flag assumptionBroken: [assumptionIDs] and its pathway status is capped at at_risk (critical assumption: off_track).

    Link confidence ∈ [0, 1]: 0.4·evidence + 0.4·assumptions + 0.2·rationale, where evidence = max strength of supporting evidence (strong 1.0, moderate 0.7, weak 0.4, anecdotal 0.2, none 0) minus half the max strength of contradicting evidence, floored at 0, assumptions = min over linked assumption statuses (validated 1.0, holding 0.8, untested 0.5, at_risk 0.25, invalidated 0), and rationale = 1 if present else 0. Path confidence = product of link confidences along the path; an outcome's confidence = max over its paths to impact. Weights are options with these defaults and are printed in every report that shows a confidence value (INV-5).

    Diff. Diff(prev, cur) lists status changes for indicators, outcomes, assumptions, and pathways, ordered per INV-3.

    6.12 Editing contract (pkg/edit)¶

    type Patch []Op // RFC 6902: add, remove, replace, move, copy, test
type Result struct {
    Document         *impact.Document
    IssuesIntroduced []validate.Issue
    IssuesResolved   []validate.Issue
    Applied          bool
}
func Apply(doc *impact.Document, p Patch, opts Options) (*Result, error) // opts.AllowErrors
    • Addressing. Standard JSON Pointers plus an ID segment: @<id> selects the element with that id in the array, e.g. /outcomes/@oc-adoption/title or /links/@ln-3. ID segments are resolved to indexes before applying; an unknown ID fails the whole patch.
    • Atomicity. Operations apply to a deep copy (INV-2). If any operation fails, or the result fails schema validation, or error-severity issues increase versus the input (unless AllowErrors), Applied is false and the original is untouched.
    • Element commands build patches: add appends (/outcomes/-) after checking ID uniqueness; set emits replace/add per flag; rm emits remove and, with --cascade, removes or rewrites references (links touching a removed outcome; IDs in appliesTo, assumptionIds, etc.).     • Writing. The CLI writes the result in canonical form (impact-model fmt), in the input's format. YAML comments are not preserved (PRD R-3).
    • Canonical form. JSON: two-space indent, struct field order, no HTML escaping, trailing newline. YAML: generated from canonical JSON. Element order is preserved; --sort orders elements by ID.

    7.3 USM / UFM integration contract¶

    • Identity: every ToC and element is addressable by §6.7 references.
    • Perspective: Perspective.actorId identifies the market participant (USM) and Perspective.futureRef (ufm:<future-slug>) groups ToCs by competing future (UFM).
    • Shared actors: ActorRegistry documents (kind: ActorRegistry, a list of Actor) let several ToCs reference the same actors; actor IDs from a registry are resolved before INV-1/INV-4 checks.
    • Alignments: BSC objectives and measures attach via Alignment with framework bsc; USM computes its scorecard from ToC Status plus its own BSC data — the ToC never stores BSC data.
    • No back-references: a ToC never lists the USM/UFM models that consume it.

    9. Security and Privacy¶

    • [x] Authentication mechanism — Not applicable: local CLI and stdio MCP; the MCP client process owns authentication.
    • [x] Authorization model — MCP path inputs confined to --root (§6.3).
    • [x] Data encryption at rest — Not applicable: files under the user's control; no storage layer.
    • [x] Data encryption in transit — Not applicable: no network I/O (INV-7).
    • [x] Audit logging — git history plus revision log.
    • [x] Vulnerability scanning — CodeQL (go-sast) and govulncheck in CI; dependencies pinned in go.sum.

    Threat model highlights: (1) untrusted documents — parser limits (max file size 10 MB, max 10,000 elements) prevent memory exhaustion; (2) user report templates run text/template with no custom functions that touch the filesystem or network; (3) restricted evidence never rendered (INV-6); (4) MCP path traversal blocked; (5) personal data — the model is designed for aggregate observations; stories identify actors by registry ID (which may be an anonymized label), quotes require consent: granted, and documentation directs users to keep personal records (contacts, sign-ups) in their source systems and import only aggregates; (6) theme coding provenance is recorded (codedBy) so model-coded stories can be audited; (7) external export tools are invoked with fixed binary names and argument vectors (no shell), on files the CLI itself wrote; (8) agent edits are confined to validated patches (INV-9), so a misbehaving agent cannot leave a document invalid without --allow-errors.

    14. Alternatives Considered¶

    Alternative Why rejected
    Hand-written JSON Schema as the source of truth Violates org Go-first policy; drifts from code
    Embed observations inside the ToC document Couples slow-changing theory with per-period data; noisy diffs; harder agent edits. Rejected for separate ObservationSet
    Model the ToC as a logframe (fixed input → activity → output → outcome → impact rows) Cannot express multiple pathways, AND/OR preconditions, or feedback; loses the ToC's main value
    Adjacency stored on outcomes (preconditions: [ids]) instead of first-class links Links need their own rationale, assumptions, evidence, and confidence; first-class edges keep those addressable
    Reuse prism-roadmap common.Assumption Lacks type, criticality, appliesTo, test, and status needed for propagation; ToC-specific type is justified, and prism-core has no assumption type
    Wrap structured-evaluation claims.Claim for evidence (as prism-roadmap assessment does) Heavier than needed for v0; revisit when evidence verification by LLM judges is in scope
    Graph database or Dolt storage Out of scope; git files suffice for document-sized graphs
    Per-outcome logic only (no groups) Cannot express nested logic such as (A AND B) OR C; ActKnowledge "clusters" and Davies' critique both call for explicit joint preconditions
    Interventions only as nodes with outgoing links (logic-model style) ActKnowledge places interventions on connectors ("what it takes for A to produce B"); both placements are supported via Intervention.targets and CausalLink.interventionIds
    Agents rewrite whole documents (no patch engine) Large, unreviewable diffs; easy to drop elements silently; no atomic validation. Patches are small, reviewable, and checkable before write
    Third-party JSON Patch library (e.g. evanphx/json-patch) Lacks ID-segment addressing and error-delta rejection; wrapping it still needs a custom resolver; the in-house engine over impact.Model JSON is small and fully tested
    Generate PPTX directly from Go Large dependency and layout effort; Marp gives Markdown-native decks consistent with prism-maturity, with PDF/PPTX export as an optional step
    Import Google Drive SDK into this module to publish and read reviews Couples a spec library to one cloud; violates INV-7; the file-based ReviewResponse lets any channel (Google, Microsoft 365, email, workshop notes) feed the same import
    Apply review responses directly Free-text feedback needs judgment; proposals plus impact-model patch keep a human decision on every change and keep INV-9
    Marp PPTX for shared decks Marp's PPTX is image-based, so Google Slides conversion yields non-editable, unreadable slides; Pandoc PPTX keeps native text
    Judge inside this module via an LLM SDK Violates the no-LLM-dependency non-goal; bundle + verdict files let any judge (agent, visionspec, visionstudio) participate and keep results auditable
    Closed enum for outcome category Development (ORS, COM-B), market-systems (AAER), and corporate ToCs need different taxonomies; category is an open string with documented recommended vocabularies
