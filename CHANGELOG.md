## [v0.5.0] - 2026-11-01

### Highlights

- Problem trees: the core problem with its causes (roots) below and effects (branches) above, drawn with arrows flowing upward from a JSON diagram spec, and checked so every cause and effect is addressed or set aside
- Causes and effects form a network: each can lead to several others, and a tree is the case of one parent each (breaking: `parent` is now `parents`)
- Every PRISM export from an AI agent: the MCP tool `impact_export` writes the OKR, outcome-journey, V2MOM, and DMAIC documents through the same service as the command line

### Added

- Problem tree effects: `effects` are the branches of the problem tree, what the core problem leads to, directly or through other effects; outcomes name the effects they relieve with `addressesEffects`. Validation reports an effect without a statement (VAL-EFF-001), one among its own parents (VAL-EFF-002), a looping chain (VAL-EFF-003), and one set aside without a reason (VAL-EFF-004)
- `report problem-tree`, `problem-tree-d2`, and `problem-tree-json` draw the core problem with causes below and effects above, arrows flowing upward, from a JSON diagram spec; the Markdown reports add tables of what addresses each cause and effect
- Lint rules IMP-EFF-001 and IMP-EFF-002 check that effects are relieved, and by long-term or impact outcomes; IMP-CAU-003 reports a cause that contributes to a deeper one; 72 rules in all
- The `effect` element command, and `--relieves` on outcomes
- The MCP tool `impact_export` exports the OKR, outcome-journey, V2MOM, and DMAIC documents, with the latest values and status when observations are given; a model the format cannot be drawn from is refused, naming what to add
- `service.ExportPRISM` draws every PRISM export, so the command line and the MCP server refuse the same models with the same errors; `prismx.Omission` has camelCase JSON fields

### Changed

- A cause's `parent` is now `parents`, a list, so causes form a network and a tree is the case of at most one parent each; causes also take provenance. In Go, `impact.Cause.Parent` is now `Parents []string` (breaking for documents and Go code that set `parent`)
- The definitions pack opens with the problem tree when the model records causes or effects. In Go, `report.Definitions` takes the impact model and returns an error: `Definitions(whole, pathways, doc) (string, error)` (breaking for Go callers)

### Fixed

- The examples linked their causes the wrong way round, from the nearer cause to the deeper one; they now point from deeper causes toward the problem

### Documentation

- A problem tree guide maps each part of the diagram to the model, says which way links point, and how the tree is laid out; the examples gain effects
- The authoring, CLI, examples, and getting-started guides cover effects and the problem tree; release notes for v0.5.0
- The README and the documentation home list the problem tree among the projections, the problem, causes, and effects in an impact model, and the journey, V2MOM, and DMAIC exports; a test keeps their shared sections identical
- Credits name problem-tree analysis in the logical framework approach, V2MOM, Six Sigma's DMAIC, and Shewhart's control charts, and the PRISM exports' use of prism-roadmap's goals packages
- The reports and getting-started guides list what the definitions pack contains, and the MCP guide and TRD list `impact_export` and `impact_diff`

### Tests

- Problem tree layering is checked for networks, rejected and set-aside elements, loops, and upward edges, and the three reports are checked against golden files; validation and lint rules are checked by seeding each defect

## [v0.4.0] - 2026-11-01

### Highlights

- A V2MOM projection: `export v2mom` draws the vision and values from the context, one method per pathway, measures from each pathway's North Star and guardrails, and obstacles from risks and open assumptions
- A DMAIC projection: mark a pathway `projections: [dmaic]`, let lint check that it is measured often enough, and `export dmaic` writes metrics with data points, control limits, root causes, initiatives, and phases
- The impact model is described as a causal model, and a fictional course-catalog example shows a program run with DMAIC

### Added

- `export dmaic` writes the pathways marked `projections: [dmaic]` as a DMAIC metrics document: one category per pathway, each indicator with a numeric baseline and target as a metric, observations as data points, individuals-chart control limits from 20 or more points, root causes from the problem tree, interventions as improvement initiatives, and a phase derived by a documented convention. Indicators left out are named on standard error
- `pathway.projections` marks what else a pathway is meant for; `dmaic` marks a program measured often enough to improve with DMAIC. Validation reports an unknown or repeated projection (VAL-PTH-007)
- Lint rules IMP-DMA-001 to IMP-DMA-003 check that a DMAIC pathway's indicators state a frequency and data source, are measured at least 20 times a year, and, for surveys, get at least 30 responses per measurement; 69 rules in all
- `export v2mom` writes the impact model as a V2MOM: the vision and values from the context, one method per pathway with its interventions as projects and its North Star, one metric, and guardrails as measures, and obstacles from risks and from high or critical assumptions not yet shown to hold, by their assessed status with `-O`. A model without a vision, values, or a pathway is refused with a message naming what to add
- `context.values` lists the principles that guide how the organization works, most important first. Validation reports a value without a name (VAL-DOC-006) and a repeated value (VAL-DOC-007)

### Changed

- The OKR export uses the OKR types of `prism-roadmap/goals/okr`, the goal types shared across the PRISM tools, in place of `structured-goals`. The exported JSON is unchanged, but `prismx.ToOKR` now returns `*okr.OKRDocument` from `github.com/grokify/prism-roadmap/goals/okr`, so Go callers change that import (breaking for the Go API only)

### Documentation

- A DMAIC guide says which programs suit DMAIC, what lint checks first, how each part of a DMAIC document maps to the model, how control limits and phases are derived, and what is left out
- A fictional course-catalog example: a free on-demand certificate catalog run with DMAIC, with weekly indicators and 24 weeks of observations
- A V2MOM guide maps each part of a V2MOM to the impact model, with one pathway followed end to end, what the V2MOM leaves out, and how to fix a refused export
- The README describes the impact model as a causal model, and the glossary says how each projection names an intervention
- Release notes for v0.4.0

### Build

- `github.com/grokify/structured-goals` is no longer a dependency, and the third-party notices drop it
- Bumped `github.com/grokify/prism-roadmap` from v0.21.0 to v0.22.0 and `github.com/grokify/prism-core` from v0.5.0 to v0.6.0

### Tests

- The V2MOM and DMAIC exports are checked against prism-roadmap's own validation, for the documented mapping, for refusals, and for determinism; the DMAIC rules are checked by seeding each defect and repairing it
- Each example, including the new course catalog, stays valid, canonical, fictional, and exportable

## [v0.3.0] - 2026-11-01

### Highlights

- The project is now `impact-model`, an AI-native format from ProductBuildersHQ: one impact model, with the theory of change, the logic model, the outcome map, the logframe, and OKRs as projections of it, none of them a part of another (breaking)
- The first release under the module path `github.com/ProductBuildersHQ/impact-model` and the command `impact-model`

### Changed

- The project is now the impact model, and the theory of change, the logic model, the outcome map, the logframe, and OKRs are projections of it. The module is `github.com/ProductBuildersHQ/impact-model`, the command is `impact-model`, and the packages are `pkg/impact` and `pkg/impactio`, with the root type `Model`
- The document says `kind: ImpactModel` (and `ImpactModelStatus` for a status), the schemas are `impact-model` and `impact-model-status`, and a file is named `impact-model.yaml`. The fields `tocId` and `childToc` are `modelId` and `childModel`, and a cross-document reference starts `model:` where it started `toc:`
- Lint rule IDs start `IMP-` where they started `TOC-`, the `--toc` flag is `--model`, the MCP tools are `impact_*`, and the agent skills are `impact-*`
- Help text, messages, and reports say impact model where they said theory or Theory of Change. The workshop deck keeps Theory of Change in its title

### Documentation

- The README and the docs index lead with the impact model as the format and list its projections, from the theory of change to OKRs, with the command that draws each and V2MOM marked as planned; the concepts page and the ADR use projection for a method's rendering, apart from `report.View`
- ADR 0001 records the rename: what changed, what did not, and the alternatives
- Third-party notices include d2vision, which the layered logic model diagram compiles in
- Release notes for v0.3.0, with a table of every old name and its new one

### Build

- Depend on oscompat v0.13.0 ([`b97e62c`](https://github.com/ProductBuildersHQ/impact-model/commit/b97e62c))

## [v0.2.0] - 2026-11-01

### Highlights

- Headline metrics: a North Star, one metric that matters, and guardrails for each program or product, and a short, ordered headline list for each audience
- 18 more lint rules, 66 in all, that check the chain from activity to impact, headline lists, and North Stars
- A layered logic model diagram that draws columns from inputs to impact with an arrow wherever the theory says one leads to another, in D2 and Mermaid
- Indicators can be worked out from others, such as a cost per outcome, and an estimated value is shown as an estimate
- The `intermediate` outcome level is now `medium_term` (breaking)

### Added

- Headline lists: an audience leads with a short, ordered, worded list of indicators, and the story report and deck use it
- A North Star, one metric that matters, and guardrails for a program or product, set in the pathway's `focus`; a `product` pathway kind
- `context.mission` and `context.vision`, so purpose is stated without being part of the causal chain
- `composedOf` on an indicator: a ratio, product, sum, or difference of other indicators, such as a cost per outcome, worked out from observed values
- The `headline` and `metric-tree` reports, and `--audience` and `--pathway` to narrow them
- 18 lint rules for the chain from activity to impact (`INT-003` to `INT-007`), headline lists (`AUD-002`, `HLN-001` to `HLN-004`), North Stars (`NSM-001` to `NSM-007`), and framing (`CTX-001`)
- Flags `--north-star`, `--one-metric`, `--guardrails`, `--composed-op`, and `--composed-of`
- A layered logic model diagram: a column for each stage from inputs to impact, a box for each item, and an arrow wherever the theory says one leads to another. Reports `logic-model-layered` (Mermaid) and `logic-model-d2` (D2, with a grid that keeps each stage in its column), and a slide beside each logic model table in the workshop deck
- `Document.IndicatorTier`, `IndicatorServes`, and `IndicatorPathways`, so every rule and report agrees on where an indicator sits in the chain and which pathways it serves

### Changed

- The `intermediate` outcome level is now `medium_term`, so short, medium, and long term form one series. Documents that use `level: intermediate` must use `level: medium_term`
- An estimated latest value is shown as an estimate, with its observation note, in every report
- The story deck tells an audience's whole headline list instead of the first five indicators in file order
- Lint rules that decide which pathways an indicator serves ask the document, so they agree with the reports

### Documentation

- Credits for the methods and projects the specification builds on, in the README and on a credits page, with the license notices of the dependencies compiled into the command line
- Diagrams of how the chain, its metrics, and each audience's headline numbers fit together, in the README and the docs index
- Guides for tiers, North Stars, headline lists, mission and vision, composed indicators, the layered logic model diagram, and the new reports and lint rules

### Build

- Depend on d2vision v0.5.0 for diagram specs
- Third-party notices and the script that generates them

### Tests

- Each chain, headline, and North Star defect is seeded and repaired in a test, so every new rule is shown to fire and to go quiet once the defect is fixed
- Reports for headline lists, estimates, the metric tree, and the layered diagram are checked against golden files, and the D2 is compiled when the d2 tool is installed

## [v0.1.0] - 2026-10-30

### Highlights

- A Go-first Theory of Change model with generated JSON Schemas, a validated edit engine, and the `theoryofchange` CLI
- Quality checks: structural validation, 48 lint rules, and a rubric for LLM-as-a-Judge review
- Measurement of indicators, outcomes, and pathways from observations, with assumption propagation and confidence
- Reports, four slide decks, and Word, PowerPoint, and CSV export, plus a review round trip
- An MCP server with ten tools and five agent skills

### Added

- Model: outcomes at five levels, precondition groups (`all`, `any`, `at_least`), causal links with polarity and feedback, interventions, assumptions, indicators, actors, evidence, and pathways
- Provenance for every element (`stated`, `inferred`, `hypothesis`, `confirmed`, `rejected`) and a ceiling of accountability
- Change analysis: responsibility for each outcome, a problem tree, target groups, audiences, and a story codebook
- Measurement design: a shared metric library, a glossary, selection criteria, a collection plan, and a budget
- Seven JSON Schemas generated from the Go types and embedded: `theory-of-change`, `observation-set`, `theory-of-change-status`, `status-diff`, `actor-registry`, `review-response`, and `csv-mapping`
- Canonical YAML and JSON with a stable content hash; `fmt`, `init`, and `schema` commands
- `<element> add|set|rm` for twenty element kinds and `patch` for RFC 6902 JSON Patches with `@id` pointers, applied atomically and rejected when they add errors
- `diff` compares two versions by element ID and drafts a revision record
- `validate` checks the schema and structure, observation sets, children against a parent, and competing futures that share an actor registry
- `lint` with 48 rules and `draft`, `standard`, and `full` profiles, reporting as a structured-evaluation summary
- `graph` queries upstream and downstream, paths, cycles, orphans, dead ends, and levels, with Graphviz output
- `judge show|record|summary` with a core rubric of 12 categories, a development addendum, and four aggregation modes
- `import observations` loads a spreadsheet through a column mapping and reports every unmatched row
- `status` computes indicator, outcome, pathway, link, and assumption status as of a date, with rollups, assumption caps, rule-based confidence, and a comparison to an earlier snapshot
- Eleven definition reports: pathway, logic model, logic-model diagram, outcome map, logframe, metrics, metric selection, collection plan, glossary, assessment, and definitions
- Twelve status reports, including executive, results, assumptions, story, learning review, portfolio, narrative, and custom templates
- Consent and sensitivity gating for stories and quotes; restricted evidence is never rendered
- Four Marp decks: workshop, executive, learning review, and audience story
- `export` to CSV, Word, PowerPoint, and OKR and outcome-journey JSON for the PRISM tools, each stamped with the theory's version and hash
- Review round trip: `export review-packet` and `export review-sheet`, `import review`, and `approve`
- `mcp` serves ten tools over standard input and output, with file paths confined to a root directory
- Five agent skills: draft from sources, author, status refresh, learning review, and audience story
- Three fictional examples: a membership network, a market-adoption theory, and three competing futures

### Documentation

- User guides, a CLI reference, and release notes published as a MkDocs site
- Research brief, concepts-to-types map, product and technical specifications, and the integration contract draft for USM and UFM

### Tests

- Golden files for every report, deck, and table; every example checked for validity, canonical form, and fictional URLs
- Seeded-defect tests for every lint rule, a patch engine suite covering every operation and failure, and a run of each agent skill's steps against the examples
- Time budgets enforced on a large theory, and the tests compile for Windows with line endings pinned by `.gitattributes`
